# T0957 Result

## Outcome

Completed implementation and local verification. Production release verification is performed
after merging and pushing the implementation commit.

## Scope delivered

- Read-only Woo synchronization imports core tax settings, classes and bounded rates. Migration 23
  stores an account/connection policy snapshot and shipping-method taxability. Full sync refreshes
  settings; the lightweight orders poll bootstraps missing tax configuration.
- New web manual orders use a debounced local tax preview. The server recalculates independently
  from current catalog tax classes, variation inheritance, customer address, net shipping method
  costs, inclusive/exclusive prices, compound priorities and line/subtotal rounding. All arithmetic
  uses integer minor units and BigInt intermediate precision; no statutory rate is hardcoded.
- Store-tax mode ignores client-calculated taxes and rejects changed policy hashes, missing/stale
  settings, unsupported settings and unavailable product/shipping metadata. UI explains failures
  instead of silently saving tax as zero. City/postcode inputs support location-specific matching.
- Persisted orders retain the policy hash, original pricing input, location, rate breakdown and
  canonical net/tax totals. Status/proof/notes changes and later syncs never reprice saved orders.
  Financial edits explicitly recalculate. Existing API manual-tax mode remains compatible.
- Canonical net unit values and saved tax totals flow through existing details, XLSX and PDF
  snapshots. Invoice subtotal now uses the pre-discount subtotal so discounts are not shown twice.

## Database and deployment

- Migration 23 adds `woo_tax_policies` with `(account_id, connection_id)` primary key and nullable
  `woo_shipping_rates.tax_status`. It is automatically applied on API startup; existing orders are
  not repriced. No new environment variable is required.
- Read-only Woo keys must be allowed to read core settings, tax rates/classes and shipping zones.
  After deployment a full sync loads the tax and shipping configuration. No Woo plugin update is
  required for these standard REST reads.

## Security, tenancy, money/time and idempotency review

- HTTP account identity comes exclusively from authenticated membership. Local preview is read-only;
  creation retains existing operation permissions/CSRF. No remote mutation interface was added.
- Every policy/catalog/shipping lookup is account scoped. Stored settings contain no credentials.
  Audit summaries contain only safe codes, policy hash, enabled flag and rate count, not addresses.
- Policy upsert replaces the same account/connection row; duplicate syncs do not duplicate audit
  events when policy/error state is unchanged. Existing durable synchronization retries are reused.
- Manual orders retain `syncPolicy=never` and `inventoryPolicy=ignore`. Financial snapshots are UTC
  timestamped, versioned, immutable under background synchronization and used by existing exports.

## Known limitations

- Automatic calculation supports EGP/two-decimal core stored tax rates. It does not claim to
  reproduce arbitrary WordPress filters, external automated tax services, customer-specific tax
  exemptions, Woo coupon rules or tax/legal compliance. Known automated-tax configuration is
  explicitly rejected. Local discounts are net minor-unit reductions; local operating fees are
  untaxed and disclosed in the UI/API contract.
- Local Node 24 produces the existing engine advisory; deployment uses Node 22. Local Chromium
  verification reused the installed headless revision 1234 via an ignored cache junction because
  the current Playwright browser download timed out. No browser path change is committed.
- Production authenticated tax configuration cannot be inspected without a signed-in session.
  Public deployed asset hashes and health verify rollout separately; store parity fixtures are
  synthetic rather than production customer data.
